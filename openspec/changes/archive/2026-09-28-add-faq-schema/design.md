## Context

Two independent paths currently produce structured data for the same routes: the client-side `SEO.tsx` component (runs after hydration, builds JSON-LD in JS) and the build-time static path (hand-maintained `public/en|ua/services/<slug>/index.html` and `public/en|ua/uzhhorod/index.html` templates, which already contain hardcoded `Service`/`LocalBusiness` JSON-LD, copied into `dist/` by `scripts/seo-head.mjs` via `writePrerenderedHtml`). The FAQ question/answer text itself lives in `src/i18n/locales/en.json` / `ua.json` under `servicePages.<slug>.faq` and `uzhhorod.faq.items`, and is only ever read by the React components (`ServiceDetails.tsx`, `UzhhorodFAQ.tsx`) today — never by the build script. `seo-head.mjs` already has a `loadLocales()` helper that reads these same JSON files for a different purpose (product/events meta text), so reading FAQ arrays there is not a new pattern.

## Goals / Non-Goals

**Goals:**
- One FAQ→`FAQPage` JSON-LD conversion, driven by the same locale data the visible FAQ UI already renders, so schema can't drift from what's on the page.
- FAQPage present in both the client-hydrated DOM and the static HTML shells for service pages and the Uzhhorod page.
- No duplicate/second `application/ld+json` script tag where one already exists — merge into the existing graph.

**Non-Goals:**
- Solving the broader "body content isn't in static HTML at all" problem — that's `prerender-static-content`. This change only adds schema, not visible body markup, to the static shells (the static shells already contain some hand-authored `Service`/`LocalBusiness` schema; visible FAQ *text* in those shells remains absent until the other change lands).
- Changing how the client-side FAQ UI itself renders.

## Decisions

- **Single conversion helper.** Add a small pure function (e.g. `buildFaqPageSchema(items: {question, answer}[])`) usable from both the client component and the Node build script. Since `SEO.tsx` is a `.tsx` React module and `seo-head.mjs` is a plain ESM Node script, this can't be one shared import without a build step change; instead implement the same small conversion logic in each location (a few lines: map `{question, answer}` to `Question`/`acceptedAnswer`), keeping the *shape* identical and both reading from the same locale JSON files, so they cannot disagree on content even though the code isn't literally shared.
- **Merge into existing `@graph`, don't add a second script tag.** Client-side: extend the existing `serviceSchema`/`breadcrumbList` and `LocalBusiness` graph construction in `SEO.tsx` to append the FAQPage entity when FAQ items exist for that locale/page. Static shells: extend the existing hardcoded JSON-LD block in each service/Uzhhorod template to a `@graph` array containing the current schema plus `FAQPage`, generated by a small addition to `seo-head.mjs` that reads the locale FAQ arrays and rewrites that block the same way `applySeoHead` already rewrites meta tags.
- **Static injection happens in `seo-head.mjs`, not by hand-editing 16 template files.** Since FAQ text can change independently of the hand-maintained HTML shells, `seo-head.mjs` gains a step (parallel to `getInjectedRouteMetas`) that, for each service slug and each language, reads `servicePages.<slug>.faq` from the corresponding locale file and produces/replaces a `FAQPage` block in that route's static JSON-LD. This runs in the existing `closeBundle` pass alongside the current per-service `writeFromPublic` calls, so it stays part of `npm run build` with no new manual step.
- **Skip condition:** if a service/locale combination has fewer than 2 FAQ entries, do not add a `FAQPage` block for it in either the client or static path (avoids publishing a technically-invalid or low-value FAQPage entity).

## Risks / Trade-offs

- Duplicated (not shared) conversion logic between the `.tsx` client path and the `.mjs` build script is a small maintenance cost; mitigated by keeping the conversion trivial (a one-line `.map`) and both sides reading the same source-of-truth JSON.
- If a future FAQ answer contains HTML or very long text, `FAQPage`'s `acceptedAnswer.text` should be plain text — validate/strip if the i18n content ever includes markup (it currently doesn't).
